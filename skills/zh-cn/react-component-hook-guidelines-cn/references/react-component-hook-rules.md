本文档适用于采用 React + TypeScript + Biome 的前端项目，目标是统一组件、Hook、页面编排与业务逻辑拆分方式，降低耦合，控制复杂度，并提供一套可跨项目复用的代码组织约定。

## 1. 适用范围

- 适用于页面组件、业务组件、通用 UI 组件、自定义 Hook、页面级编排 Hook。
- 适用于常见的前端目录结构，例如 `features/`、`components/`、`hooks/`、`pages/`、`routes/`。
- 本规范优先解决职责混杂、接口过宽、分支扩散、组件膨胀等问题。

## 2. 核心原则

### 2.1 单一职责优先

- 一个组件只保留一个核心职责。
- 一个组件只做一件主要事情。
- 一个 Hook 只封装一个关注点。
- 文件长度不是根本问题，职责混杂才是根本问题。

### 2.2 组合优于堆叠

- 超过一定复杂度必须拆分子组件或自定义 Hook。
- 业务逻辑重时，优先拆成 Hook，而不是把组件堆到几百行。
- 复杂事件处理提取为自定义 Hook 或 action function。
- 复杂分支优先改成映射表、策略对象或子组件，而不是继续堆 `if/else`。

### 2.3 展示与编排分离

- 页面组件负责组装。
- 业务 Hook 负责状态。
- 纯组件负责展示。
- 展示组件与容器逻辑分离。
- UI 组件不要直接耦合 API、路由、缓存、弹窗、埋点等多种职责。

### 2.4 接口最小化

- props 保持精简，不传“大 state 对象”。
- 不要把页面级大 state 整体传给子组件，子组件只接收最小 props。
- 子组件只依赖自己真正需要的数据和回调，不为了省事直接吃整个页面返回值。

## 3. 文件与命名规范

### 3.1 组件文件

- 每个文件尽量只导出一个主要组件。
- 一个文件只导出一个主组件。
- 一个文件只定义一个主组件。
- 组件文件名和组件名一致。
- 文件名使用项目既有命名风格；若为 React 组件，文件名应能直接体现组件职责。

### 3.2 同文件辅助子组件

- 同文件允许定义 1 到 3 个仅供当前组件使用的小子组件。
- 辅助小组件可以同文件，但仅限和主组件强相关、不会复用。
- 如果辅助子组件开始被多个文件复用，必须提升到独立文件。
- 如果辅助子组件本身已经有独立状态、独立测试价值或独立样式语义，应拆文件。

### 3.3 Hook 文件

- 一个 Hook 文件优先只导出一个主要 Hook。
- Hook 文件名与 Hook 名称保持一致，例如 `use-user-profile.ts` 对应 `useUserProfile`。
- 与 Hook 强相关的小型内部工具函数可同文件存在；通用工具必须移到 `lib/` 或 `utils/`。

## 4. 组件职责边界

### 4.1 展示组件

- 只负责渲染和轻量交互。
- 不直接发请求。
- 不直接依赖路由跳转。
- 不直接操作缓存。
- 不直接决定复杂业务流程。

### 4.2 容器组件 / 页面编排组件

- 组装页面结构。
- 调用业务 Hook。
- 协调子组件之间的数据流。
- 处理路由、查询参数、缓存刷新、弹窗编排等页面级行为。

## 5. Props 设计规范

### 5.1 最小 props 原则

- props 不超过 8 个。
- 超过 8 个 props 时，必须评估是否职责过多或边界不清。
- 优先传明确字段和明确行为，不传笼统对象。

### 5.2 允许传对象的情况

- 领域对象可以传，例如 `conversation`、`message`、`user`。
- 不允许传页面级 hook 的完整返回值或万能状态包。

## 6. 复杂度控制

### 6.1 组件长度

- 一个组件建议不超过 100 行。
- 单个组件超过 150 行时必须评估拆分。

### 6.2 函数长度

- 一个函数建议不超过 30 行。
- 一个函数超过 50 行时必须评估拆分。

### 6.3 Hook 复杂度

- 一个 Hook 不超过 3 个关注点。

### 6.4 JSX 嵌套深度

- JSX 嵌套不超过 3 层。

## 7. 分支与模式扩展规范

### 7.1 if/else 控制

- 超过 3 个 `if/else` 模式分支时，优先改为策略映射。

### 7.2 新模式接入要求

- 新增模式尽量通过新增策略实现，而不是修改多个旧分支。

## 8. Hook、Utils 与组件的拆分建议

### 8.1 什么时候抽 Hook

- 状态管理逻辑被多个组件使用。
- 组件中出现较长的副作用和事件编排。
- 需要单独测试状态流转。

### 8.2 什么时候抽 utils / lib

- 纯函数。
- 与 React 生命周期无关。
- 需要跨组件复用。

### 8.3 什么时候拆子组件

- JSX 嵌套过深。
- 条件渲染块很长。
- 列表项结构复杂。

## 9. 页面、业务 Hook、纯组件的推荐分层

1. 页面组件：负责路由接入、页面布局、模块组装。
2. 页面编排 Hook：负责聚合业务 Hook，但不要输出无边界的大对象。
3. 业务 Hook：负责单一业务流程。
4. 展示组件：只消费最小 props。
5. 通用 UI 组件：不包含业务语义。
6. `lib/utils`：承载纯函数和无状态辅助逻辑。

## 10. Biome 配合方式

- Biome 负责格式、基础可读性和部分复杂度提示。
- 职责边界、props 宽度、God Component / God Hook 仍需人工评审。

## 11. 代码评审检查清单

- 文件是否只导出一个主组件。
- 组件文件名和组件名是否一致。
- 是否存在职责混杂。
- Hook 是否超过 3 个关注点。
- props 是否超过 8 个。
- 是否把页面级大 state 直接传给子组件。
- 是否存在超过 3 个的模式分支。
- JSX 是否嵌套过深。

## 12. 例外规则

- 纯展示组件略长但职责稳定。
- 同文件内存在少量只服务当前主组件的辅助子组件。
- 页面入口略长但业务逻辑已经拆到 Hook。

## 13. 实施建议

- 新增功能前，先判断应放页面组件、业务 Hook、展示组件还是工具函数。
- 组件或 Hook 出现多个变化原因时，先拆边界再继续加功能。

## 14. 一句话总结

- 页面负责组装，Hook 负责状态，组件负责展示，工具函数负责纯逻辑。
